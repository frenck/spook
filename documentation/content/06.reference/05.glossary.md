The words Spook and :term[Home Assistant] use, in plain language. Terms linked anywhere else in this documentation land here.

## Action {#term-action}

An action in :term[Home Assistant] is something that can be :term[performed]{to="performing actions"}: a "do something" step. Actions are, for example, used to control :term[devices]{to="device"} and :term[entities]{to="entity"}. For example, the `light.turn_on` action is used to turn on a light and the `media_player.play_media` action plays a media file on a media player entity.

Actions are not limited to controlling devices and entities. They also do other things, like sending a notification, starting a script, or asking a service for information and handing the answer back.

A sequential list of actions is also known as a :term[script sequence]{to="sequence"}.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/scripts/service-calls/)

## Action name {#term-action-name}

An action name is how you write an :term[action] down in YAML when it is :term[performed]{to="performing actions"}: the integration, a dot, and what it does. For example, the `light.turn_on` action is used to turn on a light and the `media_player.play_media` action plays a media file on a media player entity.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/scripts/service-calls/)

## Action response {#term-action-response}

An action response is the data an :term[action] hands back when it is :term[performed]{to="performing actions"}. There are three kinds of actions: ones that hand nothing back (the most common), ones where a response is optional, and ones that always have one. That matters when you write YAML: for an action without a response you cannot set `response_variable`, for an optional one you may, and for one that always responds, you must.

## Action targets {#term-action-targets}

Action targets are the :term[devices]{to="device"}, :term[entities]{to="entity"}, or :term[areas]{to="area"} an action works on when :term[performing an action]{to="performing actions"}. In the editor, you pick them under **Targets**; in YAML, they go under `target`. For example, `light.turn_off` with the living room as its target turns off all the lights in the living room. :term[Home Assistant] will figure out which entities it needs to turn off based on the area that is targeted.

Not all actions work with targets.

## Area {#term-area}

An area in :term[Home Assistant] is a logical grouping of :term[devices]{to="device"} and :term[entities]{to="entity"} that are meant to match areas (or rooms) in the physical world: your home. Areas are used to group devices and entities together in, for example, the living room. Areas give a better overview of your home and can be used to target :term[actions]{to="action"} to a specific area, like turning off all the lights in the living room.

[Learn more about areas in the official Home Assistant documentation](https://www.home-assistant.io/docs/organizing/areas/)

## Automation {#term-automation}

An automation in :term[Home Assistant] is a set of triggers and :term[actions]{to="action"} that are automatically performed when a trigger fires. For example, an automation can be created to automatically turn on the lights when a motion sensor detects motion. Automations are the heart of Home Assistant; it is what makes Home Assistant a home automation platform. It is the glue that binds all the other :term[integrations]{to="integration"} together, and it is what makes your home smart and comfortable. Automations can be shared in the community in the form of a :term[blueprint].

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/getting-started/concepts-terminology/#automations)

## Blueprint {#term-blueprint}

A blueprint in :term[Home Assistant] is a reusable :term[automation] or :term[script], shared and created by the community, that can be imported into your Home Assistant instance. They are a great way to learn how to automate your home and an inspiration for new automation ideas, or just an easy way to get started. Blueprints are a great method to share your automation creations with others so that others can apply them to their own homes.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/blueprint/)

## Boolean {#term-boolean}

A boolean is a data type that can only have two values: `true` or `false`.

You mostly come across this term in :term[Home Assistant] when working with :term[YAML]. In YAML, boolean values can also be written as `yes` or `no`; however, it is recommended to stick with just `true` or `false`.

Because `yes` and `no` are boolean values in YAML, they might cause confusion when you meant to use a :term[string value]{to="string"}. For example, `yes` is a boolean value, but `"yes"` is a string value.

## Condition {#term-condition}

A condition decides whether an :term[automation] or :term[script] carries on. A condition between the trigger and the :term[actions]{to="action"} is a gate on the whole run: when it does not pass, none of the actions happen.

Conditions are also used inside a :term[sequence], in an `if` or a `choose` block. There they only decide which branch runs, and a branch that does not run leaves the rest of the sequence alone.

:term[Integrations]{to="integration"} can provide their own conditions, which is how Spook adds some. Those are named after the integration providing them, like `sun.is_up` or `spook.triggered_by_user`, while the ones built into Home Assistant itself, `state` or `template`, carry no prefix at all.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/scripts/conditions/)

## Dashboard {#term-dashboard}

A dashboard in :term[Home Assistant] is a user interface that displays information and control :term[entities]{to="entity"} in your home. Dashboards are used to create a user interface to control your home, such as turning on the lights or seeing the current temperature. Dashboards are fully customizable and can be created in many different ways. There is a vibrant community that shares their dashboards so that you can get inspiration and ideas for your own dashboard.

You might come across the term "Lovelace", which is the codename originally used for dashboards.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/getting-started/concepts-terminology/#dashboards)

## Device {#term-device}

A device in :term[Home Assistant] represents a physical device in your home, but a device can also represent a web service, like one that provides weather information. Devices are a logical grouping for :term[entities]{to="entity"}. For example, a device that can measure temperature, humidity, and pressure will have three entities: a temperature sensor, a humidity sensor, and a pressure sensor. All three entities belong to the same device.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/getting-started/concepts-terminology/#devices--entities)

## Ectoplasm {#term-ectoplasm}

[Ectoplasm](<https://en.wikipedia.org/wiki/Ectoplasm_(paranormal)>) is a term used in spiritualism to denote a substance or spiritual energy "exteriorized" by physical mediums. Or the more pop-culture version: the green goo that ghosts leave behind, like in <wiki:Ghostbuster>.

Spook uses ectoplasm to add new scary advanced behavior to the functionality of :term[Home Assistant]. Internally in the [source code of Spook](https://github.com/frenck/spook), an ectoplasm is a module it can apply to a Home Assistant :term[integration].

## Entity {#term-entity}

An entity in :term[Home Assistant] represents a single data point or single function, in most cases, of a device. Entities are used to monitor physical properties or to control the functions of :term[devices]{to="device"}. Entities are the basic building blocks of Home Assistant.

Entities have a state, telling you the current condition of the entity, such as on or off, open or closed, or a temperature.

There are different types of entities. For example, a light entity is used to control a light, a switch entity is used to control a switch, and a sensor entity is used to display a sensor value.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/getting-started/concepts-terminology/#devices--entities)

## Entity ID {#term-entity-id}

An entity ID in :term[Home Assistant] is a user-definable identifier for an :term[entity]. It is used to reference the actual entity in, for example, :term[automations]{to="automation"}, :term[scripts]{to="script"}, and dashboards. The entity ID is automatically generated by Home Assistant when an entity is created for the first time.

## Float {#term-float}

A float is a datatype, and a more technical term for a number that can have a decimal point. For example, `2.5` is a float, but `2` is a valid float value as well.

You mostly come across this term in :term[Home Assistant] when working with :term[YAML]. Floats (unlike :term[strings]{to="string"}) are not surrounded by quotes in YAML and are just written as is. For example, `2.5` is a float in YAML (thus handled as a numeric value), but `"2.5"` is a string in YAML (thus handled as text).

Floats are often confused with :term[integers]{to="integer"}. They look very much alike; the difference is that floats can have a decimal point, while integers cannot. This also means that all integers are floats, but not all floats are integers.

## Floor {#term-floor}

A floor in :term[Home Assistant] is a logical grouping of :term[areas]{to="area"} that are meant to match floors (or levels) in the physical world: your home. Floors are used to group areas together that are on the same floor in your home. Floors give a better overview of your home and can be used to target :term[actions]{to="performing actions"} to a specific floor, like turning off all the lights on the first floor.

[Learn more about floors in the official Home Assistant documentation](https://www.home-assistant.io/docs/organizing/floors/)

## HACS {#term-hacs}

Home Assistant Community Store. A third-party :term[integrations]{to="integration"} store for :term[Home Assistant], for the custom integrations that do not come with a standard Home Assistant installation.

Since Home Assistant 2026.11, HACS is part of Home Assistant itself, as the :term[Marketplace]. On older versions of Home Assistant, HACS is still how you install Spook.

[Learn more on the HACS website](https://hacs.xyz)

## Helper {#term-helper}

A helper in :term[Home Assistant] is an :term[integration] you set up from **Settings** > **Devices & services** > **Helpers**. Some give you something to set by hand, like a toggle, a number or a list to choose from. Others take an existing :term[entity] (or entities), do something with it, and give you the result as a new entity. Spook adds a few of the second kind.

## Home Assistant {#term-home-assistant}

Home Assistant is an amazing free and open-source home :term[automation] platform. Track and control all :term[devices]{to="device"} at home and automate control.

Spook is a :term[custom integration]{to="integration"} for Home Assistant.

[Visit the Home Assistant website](https://www.home-assistant.io/)

## Home Assistant Link {#term-home-assistant-link}

Home Assistant Link, called :span[Home Assistant Cloud]{#term-home-assistant-cloud} before, lets you use your Home Assistant with cloud services like Amazon Alexa and Google Assistant but also provides remote access to your Home Assistant instance without having to deal with dynamic DNS, SSL certificates, and opening ports on your router.

The Home Assistant Link service is provided by [Nabu Casa](https://www.nabucasa.com). The earnings from the services provided are used to fund Home Assistant development and related projects in the open home community. Please consider subscribing to the Home Assistant Link service to support the development of Home Assistant. 🙏

[Learn more on the Nabu Casa website](https://www.nabucasa.com/)

## Influence of Spook {#term-influence-of-spook}

Spook's part in a particular feature of :term[Home Assistant]. In some cases, Spook adds completely new, previously non-existing features; in other cases, it might modify, extend, or improve existing features. Spook documents his influence, so you can easily see what features are available because of him.

## Integer {#term-integer}

An integer is a datatype, and a more technical term for a number without a decimal point. For example, `2` is an integer, but `2.5` is not.

You mostly come across this term in :term[Home Assistant] when working with :term[YAML]. Integers (unlike :term[strings]{to="string"}) are not surrounded by quotes in YAML and are just written as is. For example, `2` is an integer in YAML (thus handled as a number), but `"2"` is a string in YAML (thus handled as text).

## Integration {#term-integration}

An integration in :term[Home Assistant] is a component that allows you to integrate a :term[device] or :term[action] with your Home Assistant installation. Home Assistant comes with well over a thousand integrations out of the box, but you can also install your own custom integrations.

Custom integrations, however, are not supported by the Home Assistant project. They are not reviewed or tested by the Home Assistant development team and thus may negatively impact the stability of your Home Assistant instance.

Spook 👻 is a custom integration for Home Assistant that is available through the :term[Marketplace].

## Integration entry {#term-integration-entry}

An integration entry in :term[Home Assistant] is a configuration for an :term[integration]. In short, it is the configuration you see on the integrations page. Most integrations can be set up multiple times (like adding two Hue bridges or multiple ESPHome devices), and each of those is an integration entry.

Home Assistant's own developer documentation calls this a "config entry", and you will still see `config_entry_id` when working with it in :term[YAML]. That is a technical term from the developer sources leaking into the user space, which is why Spook says "integration entry" instead.

## Label {#term-label}

A label in :term[Home Assistant] is a tag you make up yourself, to build your own way of organizing things. You put one or more labels on :term[devices]{to="device"}, :term[entities]{to="entity"}, or :term[areas]{to="area"}. Labels filter the tables in the user interface, and you can target :term[actions]{to="performing actions"} at them in :term[automations]{to="automation"} or :term[scripts]{to="script"}.

[Learn more about labels in the official Home Assistant documentation](https://www.home-assistant.io/docs/organizing/labels/)

## List {#term-list}

A list is a datatype, and a more technical term for a collection of items. For example, a list of :term[integers]{to="integer"}: `[1, 2, 3]`.

You mostly come across this term in :term[Home Assistant] when working with :term[YAML]. Synonyms for lists are arrays and sequences. Although, a :term[sequence] in Home Assistant mostly refers to a list of :term[actions]{to="action"}.

Lists can be written in YAML in two ways. One is the square bracket syntax, like `["one", "two", "three"]`. The other puts each item on its own line, starting with a hyphen, like `- "one"` (which is the same as `["one"]`). The second one takes more lines, but reads easier, so that is the one most people use. Both of these are the same list:

```yaml
brackets: ["one", "two", "three"]
newlines:
  - "one"
  - "two"
  - "three"
```

## Marketplace {#term-marketplace}

The place in :term[Home Assistant] to install things made by the community, like custom :term[integrations]{to="integration"}, dashboard cards and themes. You find it under **Settings**, as **Marketplace**. It is built into Home Assistant since version 2026.11, and grew out of :term[HACS].

What you install from the Marketplace is made by the community, not by the Home Assistant project, which does not support it. Spook 👻 is one of those.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/integrations/marketplace/)

## My Home Assistant {#term-my-home-assistant}

My Home Assistant is a web service by the :term[Home Assistant] project that lets documentation and websites, like this one, link you straight to a page in your own Home Assistant. Learn more about it in the [My Home Assistant FAQ](https://my.home-assistant.io/faq/).

## Performing actions {#term-performing-actions}

:term[Actions]{to="action"} are performed, for example, as a step in an :term[automation] or a :term[script] sequence, or by hand from the :term[tools].

Actions are targeted toward specific :term[devices]{to="device"}, :term[entities]{to="entity"}, or :term[areas]{to="area"}. For example, performing the `light.turn_off` action on the living room area turns off all the lights in it.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/scripts/service-calls/)

## Repairs {#term-repairs}

The repairs dashboard in :term[Home Assistant] is a place where detected issues with your Home Assistant instance are listed. It is worth a look every now and then. An issue usually tells you what to do about it, often with a link to documentation, and sometimes with a button that fixes it for you. You find it under **Settings** > **Repairs**.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/integrations/repairs)

## Scene {#term-scene}

A scene in :term[Home Assistant] is a collection of :term[entities]{to="entity"} and their states. Scenes are used to set a predefined state for a group of entities. For example, a scene can set the lights in your living room to a specific color and brightness, and your media player to a specific volume. Activate the scene, and everything goes back to exactly that.

Scenes are probably one of the most underused features of Home Assistant. They are really useful, and can make your :term[automations]{to="automation"} a lot simpler.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/getting-started/concepts-terminology/#scenes)

## Script {#term-script}

A script in :term[Home Assistant] is a sequence of actions that runs when you start it, from a dashboard, or from an automation by :term[performing an action]{to="performing actions"}. Scripts are similar to :term[automations]{to="automation"}, but have no trigger: they only run when something starts them. Scripts are a great way to group a sequence of actions together that can be executed on demand and reused in multiple automations.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/getting-started/concepts-terminology/#scripts)

## Sequence {#term-sequence}

A sequence in :term[Home Assistant] is a list of :term[actions]{to="action"} that are executed in order. Sequences are used in :term[automations]{to="automation"} and :term[scripts]{to="script"} to perform multiple actions in a specific order.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/scripts)

## Service {#term-service}

Service was an ambiguous term in :term[Home Assistant]. It has been fully replaced by :term[action].

## Service call {#term-service-call}

A service call in Home Assistant has been renamed, and is now called :term[performing an action]{to="performing actions"}.

## String {#term-string}

A string is a datatype that consists of a sequence of characters. Essentially, a string is a more technical term for: text.

You mostly come across this term in :term[Home Assistant] when working with :term[YAML]. In YAML, the best practice for using strings (text) is by always surrounding them using quotes. For example, `"Hello World"`. This is not required, but it is a good practice to follow as it prevents you from running into issues with some special cases in YAML (for example, the text `off` without using quotes will not be considered a string but a :term[boolean value]{to="boolean"}).

## Template {#term-template}

Templating is an advanced feature of :term[Home Assistant] that allows you to dynamically generate values using the [Jinja2](https://palletsprojects.com/p/jinja) template engine. The syntax used for templating comes very close to the concept of programming languages and will enable you to perform complex operations on data.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/configuration/templating/)

## Template engine {#term-template-engine}

The template engine in :term[Home Assistant] is a [Jinja2](https://palletsprojects.com/p/jinja) template engine, extended with features specific to Home Assistant. The engine is used to take a :term[template], process it, and return the resulting value from it.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/configuration/templating/)

## Template filter function {#term-template-filter-function}

Filters are a special type of :term[template function] that can be used to modify the output of a :term[template]. For example, the `lower` filter can be used to convert a string to lowercase. For the syntax of filters, inspiration was probably taken from <wiki:UNIX>. The idea is that you "pipe" a value, by adding a pipe character `|`, through some filters to do something with it. For example, `{{ "SPOOK" | lower }}` will output `spook`. You can also chain filters, for example, `{{ "SPOOK" | lower | capitalize }}` will output `Spook`.

Most :term[template functions]{to="template function"} can be used as a filter as well.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/configuration/templating/)

[Learn more in the Jinja2 documentation](https://jinja.palletsprojects.com/en/3.0.x/templates/#filters)

## Template function {#term-template-function}

A template function is a function that can be used in a :term[template]. Template functions are used to perform operations on data. For example, the `now()` function returns the current date and time, and the `is_state()` function checks if an :term[entity] is in a specific state.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/configuration/templating/)

## Template function return type {#term-template-function-return-type}

When a :term[template function] is called, it returns :term[a value]{to="template function return value"}. The returned value can be of different types. For example, if it returns a numeric value, its return type might be a :term[float]. If it returns a true or false result, that would be a :term[boolean value]{to="boolean"}. There are many different types of values that can be returned.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/configuration/templating/)

## Template function return value {#term-template-function-return-value}

A template function return value is the value a :term[template function] hands back when it is called. You can use it in a next step, for example, as the input for another template function. For example, the `now()` function returns the current date and time, and the `is_state()` function returns a :term[boolean value]{to="boolean"} indicating if an :term[entity] is in a specific state.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/configuration/templating/)

## Template test function {#term-template-test-function}

Test functions are a special type of :term[template function] that can be used to check if a condition is true or false. Inside a template they use the `is` operator. For example `3 is odd` will return `True` and `3 is even` will return `False`.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/configuration/templating/)

[Learn more in the Jinja2 documentation](https://jinja.palletsprojects.com/en/3.0.x/templates/#tests)

## Tools {#term-tools}

The tools in :term[Home Assistant] are a set of tools that can be used to inspect, debug and play with your Home Assistant instance. You will find them under **Settings** > **Tools**. It may sound very technical, but don't let that scare you. They can be used to, for example, inspect the state of :term[entities]{to="entity"}, experiment with :term[performing action]{to="performing actions"}, or test and debug your :term[templates]{to="template"}.

These were called the "developer tools" and lived in their own place in the sidebar until Home Assistant moved and renamed them in 2026. Plenty of guides out there still call them that.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/tools/dev-tools/)

## Trigger {#term-trigger}

A trigger is what sets an :term[automation] going. Something happens, a state changes, a time comes round, an event is fired, and the automation runs. An automation can have several, and any one of them firing is enough.

A trigger is not a :term[condition]. A trigger is a moment; a condition is a question asked at that moment.

:term[Integrations]{to="integration"} can provide their own triggers, which is how Spook adds some. Newer ones are named after the integration and the thing they fire on, like `sun.sunset` or `spook.sequence`. Older ones are named after the integration alone and take the detail as an option, like `mqtt` or `sun` with an `event`. Both spellings work.

[Learn more in the official Home Assistant documentation](https://www.home-assistant.io/docs/automation/trigger/)

## YAML {#term-yaml}

The complex definition would be: <wiki:YAML> is a human-readable data-serialization language. But a more simplified explanation would be: It is a structure in which we can write configuration files that are readable for both humans and machines.

It is the format :term[Home Assistant] uses to store its configuration and data. Opinions are divided on whether YAML is a good or bad format or hard or easy to use. The fact remains that Home Assistant uses it a lot, and it is definitely worth learning. YAML itself really isn't that complex, but it does have some quirks that you need to be aware of. The most complex part of using YAML with Home Assistant is not YAML itself but all the things you can do with it in Home Assistant.

Don't let it scare you. You'll get the hang of it quickly.

[Read a tutorial on YAML](https://spacelift.io/blog/yaml)
