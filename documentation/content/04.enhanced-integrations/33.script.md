A script in :term[Home Assistant] is a sequence of actions you can start whenever you like: from a dashboard button, a voice command, or as an :term[action]{to="performing actions"} in an :term[automation]. Unlike an automation, a script has no trigger of its own. Write the "movie night" steps once, and use them from everywhere.

That makes a broken script sneaky. It does nothing until somebody starts it, and only then you find out one of its steps points at something that is gone. Spook looks through your scripts ahead of time, and raises a :term[repair]{to="repairs"} when it finds something wrong.

::screenshot{name="repair-script-unknown-entities" alt="A repair raised by Spook for a script."}
Spook found an issue with a script that is using non-existing entities.

::

## Repairs

Spook looks through your scripts for things that can no longer work, and tells you in the :term[repairs dashboard]{to="repairs"}. Each repair names the script and what is wrong with it.

Fixing one always goes the same way: select the name of the script in the repair, change what the repair points at, and save. Spook looks again when you save, and takes the repair away by itself. New to this? Follow [Fix your first repair](/fix-your-first-repair).

An entity, device, area, floor or label that only disabled steps (`enabled: false`) name is left alone. A disabled step does nothing, and is usually parked on purpose. Anything a running step names as well is still reported.

### Unknown referenced areas

A script targets an area that no longer exists, usually because the area was removed or merged into another. The step that uses it does nothing.

::screenshot{name="repair-script-unknown-areas" alt="A repair raised by Spook for a script."}
Spook found an issue with a script that is using a non-existing area.

::

**How to fix it:** Open the script from the repair, and in the step that uses the missing area, pick an area that exists. Or remove the step. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every area your scripts target in their actions. When that area does not exist, it raises a repair that names the script and the missing area.

As with [automations](/automation#unknown-referenced-areas), templates are read as well, for `area_entities` and `area_devices`: an area ID, or the name or an alias of an area, in any case. An entity or device ID is reported too, as these take nothing but an area; `area_entities(area_id('light.kitchen'))` gives what is in the area of that light. Only a value written out in the template is checked, and not a lookup called by a name the script gives a meaning of its own, as a variable or a field.

:::
::

### Unknown referenced attributes

A script waits for, or checks, an attribute its entity does not have, like `brightness` on a plain switch. An attribute is an extra detail an entity carries next to its state. A wait like that only ends on its timeout, and a check like that never passes. You get no error.

**How to fix it:** Open the script from the repair and use an attribute the entity has. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the attributes your scripts use: the `attribute` of state and numeric state triggers and conditions, the attribute Spook's own state trigger follows, and attributes named in templates, like `state_attr('light.kitchen', 'brightness')`. When a script uses an attribute its entity does not have, Spook raises a repair. It names the script, the attribute and the entity, and what was most likely meant when Spook is near certain of it.

A trigger waiting on an attribute that never shows up loads fine and never fires. You get no error.

Many attributes only show up some of the time: a media player that is off drops most of its own, and integrations add their own that come and go. So an attribute is only reported when Spook cannot find it anywhere: not on the entity right now, not as something that kind of entity offers in Home Assistant, and not in anything the recorder remembers the entity having. An entity the recorder does not record is only checked for attributes that differ from a real one in upper and lower case alone, like `Brightness`. An attribute or entity that is only worked out while running, from a variable for example, is not checked. Neither is a template using `states` or `state_attr` when the script gives that name a meaning of its own, as a variable, a field or a response variable.

Spook does not look right after Home Assistant starts, when the recorder is busy, but ten minutes later. After that it looks again once a reload of scripts is done, when a script is added or removed, when the entity registry changes, when an integration loads or its configuration changes, and once a day. An attribute that newly shows up on an entity is picked up the next time it looks.

:::
::

### Unknown referenced states

A script waits for, or checks, a state its entity is never in, like `On` for a light that is `on` or `off`. A wait like that only ends on its timeout, and a check like that never passes. You get no error.

**How to fix it:** Open the script from the repair and use a state the entity can be in. Picking the state from the list in the editor, instead of typing it, avoids this. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the states your scripts wait for and check: the `to`, `from`, `not_to` and `not_from` of state triggers, the `state` of state conditions, the same options of Spook's own state trigger, and in templates `is_state('light.kitchen', 'on')` and a state compared to text, like `states('light.kitchen') == 'on'`, `states.light.kitchen.state != 'off'` or `states('light.kitchen') in ['on', 'off']`. When a script uses a state its entity is never in, like `On` for a light that is `on` or `off`, Spook raises a repair. It names the script, the state and the entity, and what was most likely meant when Spook is near certain of it.

A trigger waiting for a state that never comes loads fine and never fires. You get no error.

A state named as what the entity must not be is a guard, and a guard works whatever it names: `not_to: unavailable`, `states('light.kitchen') != 'none'` or `states('light.kitchen') not in ['unavailable', 'unknown', 'none', '']`. A list works as long as one of its states can happen: `to: ["on", home]` still waits for `on`. So those are only reported for a state that differs from a real one in upper and lower case alone, like `On`. A list the state must be in is also reported when none of its states can ever happen.

Only entities whose states are a fixed set are checked: the ones Home Assistant itself lists for that kind of entity (like a light, a cover, a lock, an alarm panel or a media player), or the options the entity offers right now, like a select, a dropdown helper, or a sensor with a fixed list of values. A plain sensor, a number or a text can be anything, so those are not checked, and neither are persons and device trackers, whose states are zone names. Everything the entity was in counts as well: right now, and anything the recorder remembers. An entity whose state is set from outside of its integration, by a REST call or a Python script for example, is not checked either.

For some kinds of entity, Home Assistant itself makes sure the state is one of the set: lights, switches, binary sensors, covers, locks, valves, climate entities, and the like. There, a state that differs from a real one in upper and lower case alone, like `On`, is always reported, and anything else outside of the set when Spook has the whole history of the entity from the recorder. For the rest, the set is what is usual, not all that is possible: a media player made from a template can be in any state it likes, and a select, a dropdown helper or a sensor with a fixed list of values can get new options while running. Those only get a state reported that differs from a real one in case alone, and only when Spook has the whole history of the entity. The same goes for an entity that works out its state in a way of its own.

With an `attribute`, a state trigger or condition waits for a value of that attribute instead, and those are checked too, in the same issue: like `Heating` for the `hvac_action` of a thermostat, which is `heating`. Only attributes whose values are a fixed set: the ones Home Assistant itself lists for that kind of entity (the action of a thermostat or a humidifier, the device class of a sensor, the repeat mode of a media player, and the like), or whose values the entity offers in another attribute, like the fan modes, preset modes and swing modes of a thermostat, the effects of a light, or the sources of a media player. Home Assistant writes whatever the integration hands it for any of these, so only a value that differs from a real one in how it is written is reported, and only when Spook has the whole history of the entity. That is upper and lower case, or YAML reading what was meant as text as something else: an unquoted `off` is the boolean false, and `2` is a number, while the attribute holds the text `"off"` or `"2"`. Such a value is shown the way YAML read it, with the text that was meant in quotes. Spook's own state trigger is checked the same way when it follows an attribute, with one difference: it makes text of whatever the attribute holds and compares that with the text of its `to`, `from`, `not_to` and `not_from`. So there, a value in another case is a slip, like `Heating` for `heating`, and so is a value YAML read as a boolean or a number whose text the attribute never holds: an unquoted `off` becomes the text `False`, which a preset mode `off` never is. A `2` becomes `2`, the same text as a fan mode `"2"`, so that one is fine. A `1.0` becomes `1.0`, which is not reported against a `"1"`: a number is never taken for a slip of another number. An attribute the entity never had is not looked at here: that is an unknown attribute, which the script gets an issue of its own for.

A state or entity that is only worked out while running, from a variable or a template for example, is not checked. In templates, only a comparison with nothing else taking part in it is read: once a filter like `| lower`, a `~` or anything like it is in between, what is compared is no longer the state itself. A template is not read for `states`, `is_state` or `state_attr` either when the script gives that name a meaning of its own, as a variable, a field or a response variable.

Spook looks at the same moments as for unknown attributes: ten minutes after Home Assistant starts, after that again once a reload of scripts is done, when a script is added or removed, when the entity registry changes, when an integration loads or its configuration changes, and once a day.

:::

### Unknown referenced devices

A script uses a device that no longer exists, usually because it was removed or replaced. Conditions, waits and actions that use it no longer work.

::screenshot{name="repair-script-unknown-devices" alt="A repair raised by Spook for a script."}
Spook found an issue with a script that is using a non-existing device.

::

**How to fix it:** Open the script from the repair, and in the step that uses the missing device, pick the device that replaced it. Or remove the step. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every device your scripts use. When that device does not exist, it raises a repair that names the script and the missing device.

As with [automations](/automation#unknown-referenced-devices), only values shaped like a device ID are considered: thirty-two hexadecimal characters, which is what Home Assistant hands out. An integration taking a `device_id` that means its own hardware, such as RFLink's protocol address, is left alone.

:::
::

### Unknown referenced integration entries

An action in a script points at an :term[integration entry] that no longer exists: one setup of an integration, like your Hue bridge. This usually happens after you removed an integration and added it again: it looks the same, but the action still points at the old one, and fails when it runs.

**How to fix it:** Open the script from the repair, and pick the integration entry again in the actions it names. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the integration entries your scripts hand their actions. Plenty of integrations have actions that ask which of their integration entries to use, like Nord Pool's prices or Mealie's recipes. When a script hands one an integration entry that does not exist, Spook raises a repair. The same goes for an integration entry of another integration than the action asks for, which happens when a step is copied from an action of another integration. The repair names the script and the integration entries that go nowhere.

Home Assistant only refuses these when the step runs, so a script that runs once in a while fails exactly then. This usually happens after an integration was removed and added again: that gives it a new integration entry, with a new ID, and every action still holds the old one.

Spook only looks at the fields an action itself says take an integration entry, never at a field because of its name. Only actions that are there right now say what they take, so the actions of an integration that is not loaded are not checked. An integration entry that exists but is not loaded right now, because it is disabled or failed to set up, is not reported either: that is the state of the integration, not a mistake in the script. An integration entry worked out while running, from a template or a variable, is not checked, and neither is a disabled step.

:::
::

### Unknown referenced entities

A script uses an entity that no longer exists, usually because it was renamed, replaced or removed. The step that uses it does nothing.

**How to fix it:** Open the script from the repair, and in the step that uses the missing entity, pick the right one. Or remove the step. The guide [Fix your first repair](/fix-your-first-repair) walks you through this one for an automation, and a script goes the same way. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every :term[entity]{to="entity"} your scripts use. When an :term[entity ID] does not exist, it raises a repair that names the script and the missing entity ID.

An entity spelled out after `states`, like `states.light.kitchen.state`, is not checked when that `states` is not Home Assistant's: when a template defines its own with a macro or `{% set %}`, or the script gives the name a meaning of its own, as a variable, a field or a response variable. Used as a filter, like `'light.kitchen' | states`, it still is Home Assistant's, and still checked. An entity ID in quotes is checked wherever it is, whatever it is handed to.

:::
::

### Unknown referenced actions

A script uses an action that does not exist, usually because the integration that provided it was removed. The step fails when it runs.

**How to fix it:** Open the script from the repair and replace or remove the step. Or bring back the integration the action came from. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every action your scripts use. When that action does not exist, it raises a repair that names the script and the missing action.

Actions of an integration you disabled are not reported: switched off on purpose is not gone. Once you enable the integration again, they are checked as usual.

:::
::

### Unknown icons

A script has an icon, or hands one out, that Home Assistant does not have, usually because of a typo or a renamed icon. Whatever gets it shows an empty spot where the icon should be.

**How to fix it:** Open the script from the repair and pick an icon that exists. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the icon of each script, and at the icons its actions hand out. Only actions that say they take an icon are looked at, like `group.set`, and the actions of Spook that create areas, labels or helpers. An `mdi:` icon that is not in the Material Design Icons that come with Home Assistant is drawn as an empty spot, without an error. Spook raises a repair naming the script and the icons, and suggests the icon you most likely meant when it is nearly certain.

This usually happens with a typo, an icon that was renamed or removed, or one picked from the Material Design Icons website that is newer than the version Home Assistant comes with.

:::
::

::accordion
:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Only icons starting with `mdi:` are checked. The older `hass:` prefix, and icons from sets you added, like those from the Marketplace, are left alone.
- An icon that is a template is not checked. What it ends up as cannot be known without running it.
- Actions that are turned off are not checked: they never run.
- The list of icons is read from the frontend Home Assistant has installed. A frontend run from a development build is not taken into account, and a frontend without that list means nothing is checked.

:::
::

### Unknown referenced floors

A script targets a floor that no longer exists. The step that uses it does nothing.

**How to fix it:** Open the script from the repair, and in the step that uses the missing floor, pick a floor that exists. Or remove the step. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every :term[floor]{to="floor"} your scripts target in their actions. When that floor does not exist, it raises a repair that names the script and the missing floor.

As with [automations](/automation#unknown-referenced-floors), templates are read as well, for `floor_areas` and `floor_entities`: a floor ID, or the name or an alias of a floor, in any case. Home Assistant tries the value as an area first: the name or an alias of an area on a floor is taken as a floor ID, and finds nothing. So with an area called Attic on a floor, `floor_areas('Attic')` finds nothing, even when there is a floor called Attic, and Spook reports it. Use the ID of the floor instead, like `floor_areas('attic')`.

:::
::

### Unknown referenced labels

A script targets a label that no longer exists. The step that uses it does nothing.

**How to fix it:** Open the script from the repair, and in the step that uses the missing label, pick a label that exists. Or remove the step. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every :term[label]{to="label"} your scripts target. When that label does not exist, it raises a repair that names the script and the missing label.

As with [automations](/automation#unknown-referenced-labels), templates are read as well, for `label_areas`, `label_devices` and `label_entities`: a label ID, or the name of a label, in any case.

:::
::

### Unknown referenced conditions

A script uses a condition that no integration provides anymore, usually because that integration was removed. The whole script stops working. Home Assistant tells you the script is broken; Spook tells you which condition did it.

**How to fix it:** Open the script from the repair and remove the condition. Or bring back the integration it came from. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the conditions your scripts use. Conditions are provided by :term[integrations]{to="integration"}, so a condition that no installed integration can provide cannot be evaluated. A script like that fails validation and becomes unavailable. That is why Spook looks at unavailable scripts too: they are the broken ones.

Home Assistant does notice, but it raises a generic issue about the script. Spook names the exact conditions, so you know what to fix.

This usually means the integration that provided the condition was removed.

:::
::

### Unknown referenced triggers

A script waits for a trigger that no integration provides anymore, usually because that integration was removed. A script has no triggers of its own, so this is about a **Wait for a trigger** step. The whole script stops working. Home Assistant tells you the script is broken; Spook tells you which trigger did it.

**How to fix it:** Open the script from the repair and remove the trigger from the wait, or the whole wait. Or bring back the integration it came from. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the trigger configurations your scripts contain, such as the ones a `wait_for_trigger` step waits on. When no installed integration can provide a trigger a script waits on, the whole script goes down with it: it fails validation and becomes unavailable.

Home Assistant raises a generic issue about the script without saying which trigger caused it. Spook names the trigger.

:::
::

### Templates that can never pass

A script has a :term[template] that, the way it is written, can never be true. A template is a small piece of code between `{{ }}` that works out a value. Its condition always fails, or its wait only ends on a timeout. You get no error.

**How to fix it:** Open the script from the repair and correct the template. The usual causes: quotes around the template, missing `{{ }}`, something pasted around it, or a template that gives `on` where `true` is needed. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks in your scripts for templates that, because of how they are written, can never render what Home Assistant needs for them to pass: the `value_template` of template conditions, shorthand template conditions (`condition: "{{ ... }}"`), `wait_template`, and template triggers in a `wait_for_trigger`. Anywhere in the sequence: in an `if`, a `choose`, the `while` or `until` of a `repeat`, a condition step, nested in `and`, `or` or `not`. When one can never pass, Spook raises a repair that names the script and the templates that can never pass.

A template condition passes only when it renders `true` (any case). A `wait_template` is checked like a condition first. After that it ends when its template renders again into something that reads as true, like `on`, `yes` or `1`. One without any Jinja, or made of fixed text alone, is never rendered again, so only `true` ends it. A template trigger fires when its template goes from something that does not read as true to something that does, so one that only ever renders `on` or `yes` never fires.

The shapes this catches are the same as for automations: quotes around the template in a `>-` block, no `{{ }}` at all, YAML pasted into the template field, a YAML `#` comment inside the Jinja, and a condition that can only render `on`, `off` or another fixed text. The [automation section](/automation#templates-that-can-never-pass) explains each, and what is left alone.

Such a condition loads fine and never passes, and a wait like that only ends on its timeout. You get no error. Only the text of the template is read. Anything that depends on a state, a variable or the moment it runs is never judged. A script that failed to load is left alone: Home Assistant reports that one itself. Spook looks again whenever scripts are reloaded, which saving one in the editor does.

:::
::

### Removed users

A script only does something for a certain user, and that user was removed. A check for them never passes again.

**How to fix it:** Open the script from the repair and use a user that exists. Or remove the check. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the users your scripts name by their ID, the same way [automations are](/automation#removed-users): in templates, the ID of a user compared to text, like `context.user_id == '…'` for the user who started the script, or `state_attr('person.frenck', 'user_id') == '…'`, and the `user_id` an event trigger in a `wait_for_trigger` waits for in its `context`. When a script names a user that no longer exists, Spook raises a repair that names the script and the user IDs it cannot find.

Home Assistant gives every user a random ID and never hands the same one out twice, so an ID no user has belongs to a user that was removed. A template comparing with that ID never matches, and Home Assistant does not tell you.

What is not checked is the same as for automations. A script that gives `context` a meaning of its own, as a variable or a field, is not read either.

:::
::
