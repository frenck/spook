Automations are the heart of :term[Home Assistant]: the glue between all your :term[integrations]{to="integration"}, and what makes your home smart.

An automation that stopped working usually does so without a word. Spook tells you: it raises a repair when an automation uses something that no longer exists. It also adds actions for the times an automation should be off, or on, for a while, and one to run an automation as if one of its triggers fired.

## Actions

Spook adds three actions for automations. You find them wherever you add an action, marked with a 👻.

### Snooze

Turns an automation off for a while, and turns it back on when the time is up.

To make an automation stop for an hour, you turn it off. And then it stays off, until somebody notices. The usual way around that is a helper entity and a second automation to turn the first one back on.

Snooze does that in one action. It survives a restart of Home Assistant, because Spook stores the time the automation is due back.

The other way round, holding one on for a while, is [Turn on for](#turn-on-for).

Turn the automation back on yourself, and the snooze is cancelled.

An automation can snooze itself: a plain way to say "and not again for an hour". Snoozing stops the automation from starting again. It does not stop the run that asked, so the steps after it still happen.

**How to use it**

1. Open the automation or script that should do the snoozing, and select **Add action**.
2. Search for **snooze**, and select **Automation: Snooze 👻**.

3. Under **Targets**, choose what to snooze: one automation, several, or every automation in an area.
4. Set **Duration** to how long it should stay off, like `01:00:00` for an hour.
5. Select **Save**.

::screenshot{name="action-snooze" alt="The Add action dialog, searched for snooze, with Automation: Snooze 👻 outlined."}
Step 2: search for snooze, and select the action with the 👻.

::

Just want to see it work? [Try this action](https://my.home-assistant.io/redirect/developer_call_service/?service=automation.snooze) opens it in your Home Assistant, ready to run once.

```yaml

  duration: "08:00:00"
```

```yaml
actions:
  - action: notify.mobile_app_phone
    data:
      message: "The pool is {{ states('sensor.pool_temperature') }} degrees"
  - action: automation.snooze
    target:
      entity_id: automation.pool_temperature_notification
    data:
      duration: "12:00:00"
```

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- An automation that is already off is left alone, and Spook says so in the log. Waking it would turn on something you turned off.
- Snoozing one that is already asleep moves its wake-up time. It does not start a second snooze.
- The automation is off while it sleeps, so anything reading its state sees exactly that. There is no third state between on and off.

:::
::

### Turn on for

Turns an automation on for a while, and turns it back off when the time is up.

The other way round from [Snooze](#snooze). An automation turned on stays on, so "just for tonight" needs somebody to remember. Like the guest mode you switch on in December and find again in March.

Turn on for does that in one action. It survives a restart of Home Assistant too, because Spook stores the time the automation is due back off.

Turning the automation off yourself cancels the run, the same way turning one on cancels a snooze.

**How to use it**

1. Open the automation or script that should do this, and select **Add action**.
2. Search for **turn on for**, and select **Automation: Turn on for 👻**.
3. Under **Targets**, choose which automations to turn on.
4. Set **Duration** to how long they should stay on, like `48:00:00` for a weekend.
5. Select **Save**.

Just want to see it work? [Try this action](https://my.home-assistant.io/redirect/developer_call_service/?service=automation.turn_on_for) opens it in your Home Assistant, ready to run once.

### Run

Runs an automation as if one of its own triggers fired.

One automation with several triggers, and a `choose` on the trigger ID to do the right thing for each: a common way to build one. And one you cannot run by hand, from a script, a button or a test, because nothing fired.

Home Assistant's own `automation.trigger` runs the actions with a trigger that is not one of the automation's, so `trigger.id` is empty and the `choose` never takes its branch. It also skips the conditions by default, where Run checks them, so what runs and what the trace shows is what a real firing would give.

You name the trigger by its trigger ID. A trigger without an ID has its position as ID, counting from `0`, the same way Home Assistant numbers it: a nested `triggers:` list counts as the triggers in it, and a disabled trigger keeps its place. Leave the trigger out, and the automation's only enabled trigger is used. With several, Spook does not guess: it refuses, and names the trigger IDs you can pick from.

A disabled trigger is refused, because for real it could never fire. A templated `enabled:` is worked out again when you call Run, the way Home Assistant does when it sets the triggers up: with the automation's trigger variables, and no states to read.

The run gets the `trigger` variable that trigger would have handed it: `id`, `idx`, `alias` and `platform`. Variables set on the trigger itself are there too. What the real trigger adds about the moment it fired, like `to_state` or `event`, is up to you: put it in **Trigger data**, and it is added to the `trigger` variable. The three that say which trigger it was, `id`, `idx` and `alias`, are not yours to set there: Spook refuses a call that tries.

It runs whether the automation is on or off, like `automation.trigger` does. Off stops the triggers from firing, not a run you ask for.

**How to use it**

1. Open the script or automation that should run it, and select **Add action**.
2. Search for **run**, and select **Automation: Run 👻**.
3. Under **Targets**, choose the automation to run.
4. Set **Trigger** to the trigger ID to run it by, like `door_opened`.
5. Select **Save**.

Just want to see it work? [Try this action](https://my.home-assistant.io/redirect/developer_call_service/?service=automation.run) opens it in your Home Assistant, ready to run once.

| :term[Action]                                     | Automation: Run 👻                                                                                                                                                                                                                                                                                                                                              |

| :term[Tools]                                      | [Try this action](https://my.home-assistant.io/redirect/developer_call_service/?service=automation.run) [![Open your Home Assistant instance and show the Actions tool with a specific action selected.](https://my.home-assistant.io/badges/developer_call_service.svg)](https://my.home-assistant.io/redirect/developer_call_service/?service=automation.run) |

| **Action data parameters** |                |              |                                 |
| -------------------------- | -------------- | ------------ | ------------------------------- |
| **Attribute**              | **Type**       | **Required** | **Default / Example**           |
| `trigger`                  | :term[string]  | No           | The only enabled trigger        |
| `trigger_data`             | object         | No           | `{"to_state": {"state": "on"}}` |
| `variables`                | object         | No           | `{"reason": "testing"}`         |
| `skip_condition`           | :term[boolean] | No           | `false`                         |

The response has an entry for every automation it ran, like `{"automation.front_door": {"ran": true}}`. `ran` is `false` when the run stopped before its actions were done: the conditions were not met, something went wrong on the way (the log says what), or the automation's mode turned a second run away, like a `single` automation that is still running. The action waits for the actions to finish, delays and waits included.

:::

:::accordion-item{label="Example actions in YAML" icon="i-mdi-code-braces"}

Run the front door automation as if the door just opened:

```yaml
action: automation.run
target:
  entity_id: automation.front_door
data:
  trigger: door_opened
  trigger_data:
    to_state:
      state: "on"
```

The second trigger of an automation without trigger IDs, skipping its conditions:

```yaml
action: automation.run
target:
  entity_id: automation.hallway_lights
data:
  trigger: "1"
  skip_condition: true
```

Run it, and tell whether it did:

```yaml
actions:
  - action: automation.run
    target:
      entity_id: automation.front_door
    data:
      trigger: door_opened
      variables:
        reason: testing
    response_variable: result
  - if: "{{ not result['automation.front_door'].ran }}"
    then:
      - action: notify.mobile_app_phone
        data:
          message: "The front door automation did not run"
```

:::
:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- **Trigger data** arrives as plain data, not as the state objects a real trigger hands over: `trigger.to_state.state` works in a template, something like `trigger.to_state.last_changed` only when you put it there yourself.
- A trigger with an ID is named by that ID, not by its position.
- `platform` is the one the trigger is set up with. A trigger that hands its work to another platform names that one when it fires for real, like an MQTT device trigger that says `mqtt`. When your automation looks at it, set `platform` in **Trigger data**.
- A templated `enabled:` that reads `this` can come out differently than it did when Home Assistant set the triggers up, because the automation's own state has moved on since.
- When several triggers share an ID, the first enabled one is used. Its position, alias, platform and variables are the ones the run gets, also when the others differ in those.
- An automation that failed to set up, the ones Home Assistant shows as unavailable, is skipped by Home Assistant before Spook sees it. Nothing runs, and asking for a response gets Home Assistant's error that the action matched no entities.

:::
::

## Repairs

Spook looks through your automations for things that can no longer work, and tells you in the :term[repairs dashboard]{to="repairs"}. Each repair names the automation and what is wrong with it.

Fixing one always goes the same way: select the name of the automation in the repair, change what the repair points at, and save. Spook looks again when you save, and takes the repair away by itself. New to this? Follow [Fix your first repair](/fix-your-first-repair).

Automations that are turned off are left alone. An automation that is off does nothing, so nothing in it can go wrong yet. Often it is off exactly because something in it is broken. As soon as you turn it back on, Spook looks at it again and reports what it finds.

The same goes for an entity, device, area, floor or label that only disabled steps, triggers or conditions (`enabled: false`) name. A disabled step does nothing either, and is usually parked on purpose. Anything a running step names as well is still reported.

### Unknown referenced areas

An automation targets an area that no longer exists, usually because the area was removed or merged into another. The step that uses it does nothing.

::screenshot{name="repair-automation-unknown-areas" alt="A repair raised by Spook for an automation."}
Spook found an issue with an automation that is using a non-existing area.

::

**How to fix it:** Open the automation from the repair, and in the step that uses the missing area, pick an area that exists. Or remove the step. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every area your automations target in their actions. When that area does not exist, it raises a repair that names the automation and the missing area.

Templates are read as well, for `area_entities` and `area_devices`, called or as a filter. Handed an area that does not exist, these give an empty list and no error. So an action targeting `{{ area_entities('Living room') }}` does nothing at all once the area is renamed. Spook looks the value up the way Home Assistant does: an area ID, or the name or an alias of an area, in any case. An entity or device ID is reported too. These take nothing but an area, so `area_entities('light.kitchen')` never finds anything; `area_entities(area_id('light.kitchen'))` gives what is in the area of that light.

Only a value written out in the template is checked. One worked out while running, from a variable or by joining pieces, is not, and neither is a lookup called by a name the automation gives a meaning of its own, as a variable.

:::
::

### Unknown referenced attributes

An automation waits for, or checks, an attribute its entity does not have, like `brightness` on a plain switch. An attribute is an extra detail an entity carries next to its state. A trigger like that never fires, and you get no error.

**How to fix it:** Open the automation from the repair and use an attribute the entity has. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the attributes your automations use: the `attribute` of state and numeric state triggers and conditions, the attribute Spook's own state trigger follows, and attributes named in templates, like `state_attr('light.kitchen', 'brightness')`. When an automation uses an attribute its entity does not have, Spook raises a repair. It names the automation, the attribute and the entity, and what was most likely meant when Spook is near certain of it.

A trigger waiting on an attribute that never shows up loads fine and never fires. You get no error.

Many attributes only show up some of the time: a media player that is off drops most of its own, and integrations add their own that come and go. So an attribute is only reported when Spook cannot find it anywhere: not on the entity right now, not as something that kind of entity offers in Home Assistant, and not in anything the recorder remembers the entity having. An entity the recorder does not record is only checked for attributes that differ from a real one in upper and lower case alone, like `Brightness`. An attribute or entity that is only worked out while running, from a variable for example, is not checked. Neither is a template using `states` or `state_attr` when the automation gives that name a meaning of its own, as a variable, a field or a response variable.

Spook does not look right after Home Assistant starts, when the recorder is busy, but ten minutes later. After that it looks again once a reload of automations is done, when an automation is added or removed, when the entity registry changes, when an integration loads or its configuration changes, and once a day. An attribute that newly shows up on an entity is picked up the next time it looks.

:::
::

### Unknown referenced states

An automation waits for a state its entity is never in, like `On` for a light that is `on` or `off`. A trigger like that never fires, and you get no error.

**How to fix it:** Open the automation from the repair and use a state the entity can be in. Picking the state from the list in the editor, instead of typing it, avoids this. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the states your automations wait for and check: the `to`, `from`, `not_to` and `not_from` of state triggers, the `state` of state conditions, the same options of Spook's own state trigger, and in templates `is_state('light.kitchen', 'on')` and a state compared to text, like `states('light.kitchen') == 'on'`, `states.light.kitchen.state != 'off'` or `states('light.kitchen') in ['on', 'off']`. When an automation uses a state its entity is never in, like `On` for a light that is `on` or `off`, Spook raises a repair. It names the automation, the state and the entity, and what was most likely meant when Spook is near certain of it.

A trigger waiting for a state that never comes loads fine and never fires. You get no error.

A state named as what the entity must not be is a guard, and a guard works whatever it names: `not_to: unavailable`, `states('light.kitchen') != 'none'` or `states('light.kitchen') not in ['unavailable', 'unknown', 'none', '']`. A list works as long as one of its states can happen: `to: ["on", home]` still waits for `on`. So those are only reported for a state that differs from a real one in upper and lower case alone, like `On`. A list the state must be in is also reported when none of its states can ever happen.

Only entities whose states are a fixed set are checked: the ones Home Assistant itself lists for that kind of entity (like a light, a cover, a lock, an alarm panel or a media player), or the options the entity offers right now, like a select, a dropdown helper, or a sensor with a fixed list of values. A plain sensor, a number or a text can be anything, so those are not checked, and neither are persons and device trackers, whose states are zone names. Everything the entity was in counts as well: right now, and anything the recorder remembers. An entity whose state is set from outside of its integration, by a REST call or a Python script for example, is not checked either.

For some kinds of entity, Home Assistant itself makes sure the state is one of the set: lights, switches, binary sensors, covers, locks, valves, climate entities, and the like. There, a state that differs from a real one in upper and lower case alone, like `On`, is always reported, and anything else outside of the set when Spook has the whole history of the entity from the recorder. For the rest, the set is what is usual, not all that is possible: a media player made from a template can be in any state it likes, and a select, a dropdown helper or a sensor with a fixed list of values can get new options while running. Those only get a state reported that differs from a real one in case alone, and only when Spook has the whole history of the entity. The same goes for an entity that works out its state in a way of its own.

With an `attribute`, a state trigger or condition waits for a value of that attribute instead, and those are checked too, in the same issue: like `Heating` for the `hvac_action` of a thermostat, which is `heating`. Only attributes whose values are a fixed set: the ones Home Assistant itself lists for that kind of entity (the action of a thermostat or a humidifier, the device class of a sensor, the repeat mode of a media player, and the like), or whose values the entity offers in another attribute, like the fan modes, preset modes and swing modes of a thermostat, the effects of a light, or the sources of a media player. Home Assistant writes whatever the integration hands it for any of these, so only a value that differs from a real one in how it is written is reported, and only when Spook has the whole history of the entity. That is upper and lower case, or YAML reading what was meant as text as something else: an unquoted `off` is the boolean false, and `2` is a number, while the attribute holds the text `"off"` or `"2"`. Such a value is shown the way YAML read it, with the text that was meant in quotes. Spook's own state trigger is checked the same way when it follows an attribute, with one difference: it makes text of whatever the attribute holds and compares that with the text of its `to`, `from`, `not_to` and `not_from`. So there, a value in another case is a slip, like `Heating` for `heating`, and so is a value YAML read as a boolean or a number whose text the attribute never holds: an unquoted `off` becomes the text `False`, which a preset mode `off` never is. A `2` becomes `2`, the same text as a fan mode `"2"`, so that one is fine. A `1.0` becomes `1.0`, which is not reported against a `"1"`: a number is never taken for a slip of another number. An attribute the entity never had is not looked at here: that is an unknown attribute, which the automation gets an issue of its own for.

A state or entity that is only worked out while running, from a variable or a template for example, is not checked. In templates, only a comparison with nothing else taking part in it is read: once a filter like `| lower`, a `~` or anything like it is in between, what is compared is no longer the state itself. A template is not read for `states`, `is_state` or `state_attr` either when the automation gives that name a meaning of its own, as a variable, a field or a response variable.

Spook looks at the same moments as for unknown attributes: ten minutes after Home Assistant starts, after that again once a reload of automations is done, when an automation is added or removed, when the entity registry changes, when an integration loads or its configuration changes, and once a day.

:::
::

### Unknown referenced devices

An automation uses a device that no longer exists, usually because it was removed or replaced. Triggers, conditions and actions that use it no longer work.

::screenshot{name="repair-automation-unknown-devices" alt="A repair raised by Spook for an automation."}
Spook found an issue with an automation that is using a non-existing device.

::

**How to fix it:** Open the automation from the repair, and in the step that uses the missing device, pick the device that replaced it. Or remove the step. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every device your automations use. When that device does not exist, it raises a repair that names the automation and the missing device.

Only values shaped like a device ID are considered. Home Assistant hands those out itself and they are always thirty-two hexadecimal characters. Integrations are free to take a field called `device_id` meaning their own hardware, and some do: RFLink's `device_id` is a protocol address. Those are not devices Home Assistant knows about and never will be, so Spook leaves them alone. A real device that was removed still leaves an ID of the right shape behind, so Spook does not miss those.

:::
::

### Unknown referenced integration entries

An action in an automation points at an :term[integration entry] that no longer exists: one setup of an integration, like your Hue bridge. This usually happens after you removed an integration and added it again: it looks the same, but the action still points at the old one, and fails when it runs.

**How to fix it:** Open the automation from the repair, and pick the integration entry again in the actions it names. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the integration entries your automations hand their actions. Plenty of integrations have actions that ask which of their integration entries to use, like Nord Pool's prices or Mealie's recipes. When an automation hands one an integration entry that does not exist, Spook raises a repair. The same goes for an integration entry of another integration than the action asks for, which happens when a step is copied from an action of another integration. The repair names the automation and the integration entries that go nowhere.

Home Assistant only refuses these when the step runs, so an automation that runs once in a while fails exactly then. This usually happens after an integration was removed and added again: that gives it a new integration entry, with a new ID, and every action still holds the old one.

Spook only looks at the fields an action itself says take an integration entry, never at a field because of its name. Only actions that are there right now say what they take, so the actions of an integration that is not loaded are not checked. An integration entry that exists but is not loaded right now, because it is disabled or failed to set up, is not reported either: that is the state of the integration, not a mistake in the automation. An integration entry worked out while running, from a template or a variable, is not checked, and neither is a disabled step.

:::
::

### Unknown referenced entities

An automation uses an entity that no longer exists, usually because it was renamed, replaced or removed. The step that uses it does nothing.

::screenshot{name="repair-unknown-entities" alt="A repair raised by Spook, listing the entities an automation uses that no longer exist."}
Spook found an issue with an automation that is using non-existing entities.

::

**How to fix it:** Open the automation from the repair, and in the step that uses the missing entity, pick the right one. Or remove the step. The guide [Fix your first repair](/fix-your-first-repair) walks you through this one. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every :term[entity]{to="entity"} your automations use. When an :term[entity ID] does not exist, it raises a repair that names the automation and the missing entity ID.

An entity spelled out after `states`, like `states.light.kitchen.state`, is not checked when that `states` is not Home Assistant's: when a template defines its own with a macro or `{% set %}`, or the automation gives the name a meaning of its own, as a variable, a field or a response variable. Used as a filter, like `'light.kitchen' | states`, it still is Home Assistant's, and still checked. An entity ID in quotes is checked wherever it is, whatever it is handed to.

### Unknown icons

An automation hands out an icon that Home Assistant does not have, usually because of a typo or a renamed icon. Whatever it sets shows an empty spot where the icon should be.

**How to fix it:** Open the automation from the repair and pick an icon that exists. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the icons the actions in your automations hand out. Only actions that say they take an icon are looked at, like `group.set`, and the actions of Spook that create areas, labels or helpers. When one of those is handed an `mdi:` icon that is not in the Material Design Icons that come with Home Assistant, whatever it sets is drawn with an empty spot for an icon. Spook raises a repair naming the automation and the icons, and suggests the icon you most likely meant when it is nearly certain.

This usually happens with a typo, an icon that was renamed or removed, or one picked from the Material Design Icons website that is newer than the version Home Assistant comes with.

:::
::

::accordion
:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Only icons starting with `mdi:` are checked. The older `hass:` prefix, and icons from sets you added, like those from the Marketplace, are left alone.
- An icon that is a template is not checked. What it ends up as cannot be known without running it.
- Actions that are turned off are not checked: they never run.
- The list of icons is read from the frontend Home Assistant has installed. A frontend run from a development build is not taken into account, and a frontend without that list means nothing is checked.

:::

### Unknown referenced floors

An automation targets a floor that no longer exists. The step that uses it does nothing.

**How to fix it:** Open the automation from the repair, and in the step that uses the missing floor, pick a floor that exists. Or remove the step. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every :term[floor]{to="floor"} your automations target in their actions. When that floor does not exist, it raises a repair that names the automation and the missing floor.

Templates are read as well, for `floor_areas` and `floor_entities`, called or as a filter, in the same way as for areas: a floor ID, or the name or an alias of a floor, in any case. Home Assistant tries the value as an area first, though. When it is the name or an alias of an area that sits on a floor, it is taken as a floor ID, and nothing is found. So with an area called Attic on a floor, `floor_areas('Attic')` finds nothing, even when there is a floor called Attic, and Spook reports it. Use the ID of the floor instead, like `floor_areas('attic')`. An entity or device ID never finds a floor either.

### Unknown referenced conditions

An automation uses a condition that no integration provides anymore, usually because that integration was removed. The whole automation stops working. Home Assistant tells you the automation is broken; Spook tells you which condition did it.

**How to fix it:** Open the automation from the repair and remove the condition. Or bring back the integration it came from. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the conditions your automations use. Conditions are provided by :term[integrations]{to="integration"}, so a condition that no installed integration can provide cannot be evaluated. An automation like that fails validation and becomes unavailable. That is why Spook looks at unavailable automations too: they are the broken ones.

Home Assistant does notice, but it raises a generic issue about the automation. Spook names the exact conditions, so you know what to fix.

This usually means the integration that provided the condition was removed.

### Unknown referenced triggers

An automation uses a trigger that no integration provides anymore, usually because that integration was removed. The whole automation stops working. Home Assistant tells you the automation is broken; Spook tells you which trigger did it.

**How to fix it:** Open the automation from the repair and remove the trigger. Or bring back the integration it came from. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the triggers your automations use. Like conditions, triggers come from integrations. When no installed integration can provide a trigger, the whole automation goes down with it: it fails validation and becomes unavailable.

Home Assistant does notice, and raises a generic issue about the automation, without saying which trigger caused it. Spook names the trigger.

### Unknown referenced trigger IDs

An automation checks which trigger started it, using a trigger ID none of its triggers has. That check never passes, so whatever comes after it never runs. It usually happens when a trigger was renamed or removed, or the ID has a typo.

**How to fix it:** Open the automation from the repair, and make the two match: use the ID of one of its triggers in the check, or give the trigger the ID the check asks for. Mind upper and lower case. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the trigger IDs your automations check for: the `id` of every trigger condition, at the top of the automation and anywhere in its actions (like in a `choose`, an `if`, a `repeat`, a condition step, or nested in `and`, `or` or `not`), and in templates `trigger.id` compared to text, like `trigger.id == 'arrived'`, `trigger.id != 'left'` or `trigger.id in ['arrived', 'left']`. When an automation checks for an ID none of its own triggers has, Spook raises a repair. It names the automation and the trigger IDs it checks for that no trigger has.

A trigger condition asking for an ID that no trigger hands over loads fine and never passes. Whatever it guards never runs, and you get no error. It usually happens when a trigger was renamed or removed, or the ID has a typo: trigger IDs are case-sensitive.

A trigger without an ID of its own goes by its position in the list of triggers, counting from `0`, so a check for `1` is fine as long as the automation has a second trigger. Triggers you disabled (`enabled: false`) still count: their IDs are not unknown, they are parked.

Some things are not checked, so Spook does not guess:

- An ID that is only worked out while running, from a variable or a template for example. In templates, only a comparison with nothing else taking part in it is read, and `wait.trigger.id` is the trigger a wait ended on, not the one that started the automation.
- An automation that gives `trigger` a meaning of its own, as a variable or a response variable, and a template that does the same with `{% set %}` or the like.
- An automation that failed to load. Home Assistant reports that one itself.

An automation on a blueprint is checked with its inputs filled in, the way Home Assistant runs it. Spook looks again whenever automations are reloaded, which saving one in the editor does.

:::
::

### Templates that can never pass

An automation has a :term[template] that, the way it is written, can never be true. A template is a small piece of code between `{{ }}` that works out a value. Its condition always fails, its trigger never fires, or its wait only ends on a timeout. You get no error.

**How to fix it:** Open the automation from the repair and correct the template. The usual causes: quotes around the template, missing `{{ }}`, something pasted around it, or a template that gives `on` where `true` is needed. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks in your automations for templates that, because of how they are written, can never render what Home Assistant needs for them to pass: the `value_template` of template conditions and template triggers, shorthand template conditions (`conditions: "{{ ... }}"`), and `wait_template`. Wherever they are: at the top of the automation, and anywhere in its actions (an `if`, a `choose`, the `while` or `until` of a `repeat`, a condition step, nested in `and`, `or` or `not`, a `wait_for_trigger`). When one can never pass, Spook raises a repair that names the automation and the templates that can never pass.

What passes differs per kind. A template condition passes only when it renders `true` (any case). A template trigger fires when its template turns into something that reads as true: `true`, `on`, `yes`, `enable`, `1` or another number that is not zero. It has to see something that does not read as true first, so one that only ever renders `on` or `yes` never fires. A `wait_template` is checked like a condition first. After that it ends when its template renders again into something that reads as true. One without any Jinja, or made of fixed text alone, is never rendered again, so only `true` ends it.

The shapes this catches, all seen on the forums:

- Quotes around the template in a block. With `value_template: >-` followed by `"{{ is_state('light.hall', 'on') }}"`, the quotes are text, so the result is `"True"`, quotes included.
- No `{{ }}` at all. `value_template: "is_state('light.hall', 'on')"` is not a template, it is that text. One missing `{{` does the same.
- YAML pasted into the template field of the editor, like `- condition: template` followed by its `value_template:`. All of it is text around the template, and ends up in the result.
- A YAML `#` comment inside the Jinja. Jinja does not know YAML comments: it prints them.
- A condition that can only render `on`, `off` or another fixed text besides `true`, like `{{ 'on' if is_state('light.hall', 'on') else 'off' }}`. Fine for a trigger, never passing for a condition.

A template condition, trigger or wait like that loads fine and never passes. The condition is false, the wait only ends on its timeout, the trigger never fires. You get no error.

Only the text of the template is read. Spook raises the issue only when that alone settles it: text that is always part of the result and can never be part of `true`, a result that always starts with something nothing true starts with, or every result the template can give, whichever way it goes, failing. Anything that depends on a state, a variable or the moment it runs is never judged. Some things are not reported on purpose:

- A template trigger without any Jinja that does read as true, like `true` or `on`. It never changes, so it never fires either, but that is not what this repair is about.
- A comment after the template in a trigger, like `{{ is_state('light.hall', 'on') }} # hall`. Home Assistant reads a trigger's result like Python, and Python skips that comment, so it works.
- Text that is only printed in some branches of an `{% if %}` or a loop.
- An automation that failed to load. Home Assistant reports that one itself.

An automation on a blueprint is checked with its inputs filled in, the way Home Assistant runs it. Spook looks again whenever automations are reloaded, which saving one in the editor does.

:::
::

### Removed users

An automation only reacts to a certain user, and that user was removed. A trigger waiting for them never fires again.

**How to fix it:** Open the automation from the repair and pick a user that exists. Or remove the check. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the users your automations name by their ID: the `user_id` an event trigger waits for in its `context`, also in a `wait_for_trigger`, and in templates the ID of a user compared to text. That is the user behind something, like `trigger.to_state.context.user_id == '…'`, `trigger.event.context.user_id in ['…', '…']` or `context.user_id != '…'`, and the user of a person, like `state_attr('person.frenck', 'user_id') == '…'` or `is_state_attr('person.frenck', 'user_id', '…')`. When an automation names a user that no longer exists, Spook raises a repair that names the automation and the user IDs it cannot find.

Home Assistant gives every user a random ID and never hands the same one out twice, so an ID no user has belongs to a user that was removed. A trigger waiting for that user never fires for them, and a template comparing with that ID never matches. Home Assistant does not tell you.

Some things are not checked, so Spook does not guess:

- Something that is not shaped like a user ID. A user written down by name never matched anybody, and is not a user that was removed.
- `user_id` in the `event_data` of an event trigger, or in the data of an event in a template. What an event calls `user_id` is up to whoever fires it, like the Telegram user of a Telegram command.
- An attribute called `user_id` of anything but a person.
- A comparison something else takes part in, like a filter, and a template or automation that gives `trigger`, `context` or the like a meaning of its own.
- A disabled step or trigger, and an automation that is turned off or failed to load.

Spook looks again whenever a user is added or removed, and whenever automations are reloaded, which saving one in the editor does.

:::
