A :term[blueprint] in :term[Home Assistant] is a reusable :term[automation] or :term[script], most often shared and created by the community, that can be imported into your Home Assistant instance.

They are a good way to learn how to automate your home, to get new ideas, or just to get started. And they are how people share their automations, so others can use them in their own homes.

Spook tells you when the author of a blueprint you imported changed it, and lets you install that change from the updates page, like any other update. It also adds an action to import a blueprint straight from a URL.

## Devices & entities

Spook adds one update :term[entity] for every :term[automation] or :term[script] blueprint you imported from a URL. When the author changes the blueprint, it shows up at the top of **Settings**, next to your other updates.

There is no :term[device] for them. A blueprint is a file, and the updates page names a row by the device it belongs to. Putting them all on one device would leave every row saying the same thing.

### Updates

_Default :term[entity ID]: `update.<blueprint name>`_

Tells you when a blueprint you imported changed at its source, and installs that change for you.

When you import a :term[blueprint], Home Assistant writes down where it came from. After that, the address is not checked again. The blueprint's author can fix a bug in it a week later, and you would only know by opening the forum topic and reading the YAML yourself.

Spook follows that address for you, roughly once a day, and offers an update when what is there no longer matches what you have.

**How to use it**

1. Go to **Settings**. A blueprint with something new is listed at the top, by its name, with your other updates.

::screenshot{name="blueprint-update-row" alt="The updates at the top of the Settings page, listing an update for the blueprint Light on when a door opens."}
A blueprint update, at the top of **Settings**.

::

2. Select it. The dialog tells you what changed, which of your automations or scripts use it, and whether the update would stop any of them from loading.
3. Turn on **Create backup**. It keeps a copy of the blueprint you have now, so you can go back.
4. Select **Update**.

Installing fetches the blueprint again and writes it over the copy you have, exactly as Home Assistant's own re-import button does. Then it reloads every :term[automation] and :term[script] that uses it. The backup is worth having: if you ever edited that blueprint yourself, your edits are what gets written over.

The entities are ordinary update entities, so you can use them in an automation of your own too, for example to send a notification when one of them has something new.

"Roughly once a day", because each round picks its own moment for the next one, somewhere in the following few hours. A fixed hour would have every installation that restarted after the same release knocking on the community forum at the same time, every day.

Only blueprints that came from a URL get one. A blueprint you wrote yourself has no source to check against. The three example blueprints Home Assistant lays down for you are left alone as well: they point at Home Assistant's development branch, which is not the version you are running.

Only automation and script blueprints, too. Those are the only two kinds whose users Home Assistant can list. Without that list, there is no way to tell whether an update would leave one of them unable to load. So template blueprints are left out until there is a way to check them.

Delete a blueprint, or take the source address back out of it, and the update :term[entity] goes with it. Blueprints raise no events, so Spook notices on the next round, not at the moment it happens. One deleted while Home Assistant was stopped is caught the next time Spook starts, so you are not left with an entity in the list and no blueprint behind it.

#### Where the copies go

Beside the blueprint itself, in the same folder, with the date and time it was put there added to the filename:

```text
config/blueprints/automation/frenck/motion_light.yaml
config/blueprints/automation/frenck/motion_light.yaml.2026-08-31_204512.bak
config/blueprints/automation/frenck/motion_light.yaml.2026-08-24_091133.bak
```

So a copy sits next to the blueprint it belongs to, wherever in `blueprints/` that blueprint lives. The time is your local time, not UTC. The newest three per blueprint are kept, and installing a fourth update removes the oldest.

To go back to one, rename it over the blueprint it is a copy of and reload your :term[automations]{to="automation"} or :term[scripts]{to="script"}. A `.bak` file is nothing special to Home Assistant, so whatever you already use to reach your configuration folder will do, like the File editor or Studio Code Server add-ons, Samba or SSH. There is no action for it: putting one back is a rename, and the file is already there.

The extension does not end in `.yaml`, on purpose. Home Assistant reads every `.yaml` file under the blueprint folders as a blueprint, so a copy named that way would turn up in your blueprint list, and be given an update entity of its own.

#### What the update dialog tells you

::screenshot{name="blueprint-update-dialog" alt="The update dialog of a blueprint: where it was imported from, the warning, what changed compared with your copy, the automation using it, the line by line comparison folded, Create backup and Update."}
The update of a blueprint that now turns the light off again after a while.

::

Every other update dialog in Home Assistant shows you release notes. This one cannot, because there are none: a blueprint has no changelog, and the author does not have to say anything anywhere.

So the dialog shows the next best thing. First, the address the blueprint came from, as a link, so you can read what changed before deciding. Second, a warning. An author improving their blueprint does not mean it still suits the :term[automations]{to="automation"} you built on it: inputs get renamed, and behaviour gets rethought.

It also tells you what changed. That is Spook comparing the two files, not the author saying anything:

```text
**Compared with the copy you have:**
- **New settings**: Wait time
- What it does **changed**
```

| Put a selector on an input                                | **Settings changed**: Motion sensor                                                                         |

| Changed when it fires                                     | When it runs **changed**                                                                                    |
| Changed the mode                                          | How it handles overlapping runs **changed**                                                                 |
| Moved two settings around, or gathered them into sections | **The settings are arranged differently**                                                                   |
| Said it no longer needs a particular Home Assistant       | It **no longer asks** for a particular Home Assistant version                                               |
| Rewrote it, 80 things changed                             | **New settings**: 80, What it does **changed**, When it runs **changed**                                    |

:::
::

Settings are named as their author named them, up to three of them. Past that you get the count: eighty names is a wall of text, and they are all in the blueprint for whoever wants to read them.

The rename in that table is the one this exists for. Say an author changes the key an input is stored under, and leaves its label alone. You get two settings that read exactly the same. Whatever you filled in sits under the old key, and the new version never looks there. So the key is shown whenever a label on its own would not tell them apart.

And if Spook cannot read the copy you have at that moment, it says so. Saying nothing would read as "nothing changed".

Underneath that, what is built on the :term[blueprint]. An update writes over a file other things are running on, and Home Assistant does not show you which ones anywhere else:

```text
**The following 2 automations are using this blueprint:**

- [Hallway light](/config/automation/edit/hallway)
- [Porch light](/config/automation/edit/porch)
```

Each one links to its editor, so you can go and look at what an update is about to reach before you install it. An :term[automation] written in YAML without an `id:` has no editor to open, so that one links to the overview page instead. And when nothing is built on it, you get told that too. It means you can install without reading any further.

And underneath that, the difference itself. It is folded away, because most people only want the sentence above it.

::accordion
:::accordion-item{label="Technical details" icon="i-mdi-cog-outline"}

What that difference looks like:

```text
@@ -7,11 +7,14 @@
       name: Motion sensor
     light_target:
       name: Light
+    wait_time:
+      name: Wait time
+      default: 120
 trigger:
 - platform: state
   entity_id: !input motion_entity
   to: 'on'
 action:
-- service: light.turn_on
+- service: light.toggle
   entity_id: !input light_target

```

Both sides go through Home Assistant's own YAML writer before being compared. Without that, the file on your disk (written by Home Assistant) and the one just fetched (in its author's layout) differ in indentation and quoting before they differ in anything that matters. That came to eleven lines on an eighteen-line :term[blueprint] that had not changed at all, and hundreds on a large one. Written out the same way, only the real changes are left. Past a hundred lines it stops and says how many more there were, because all of it travels to your browser whether you open it or not. And a :term[blueprint] past a few thousand lines is not compared line by line at all. The work grows with the square of the length: on a real one of 36,000 lines it took ten seconds, for something that would be cut to a hundred lines anyway.

:::
::

**What an update is going to cost you comes first**, above everything else. Nobody reads to the bottom for a headline. What changed and what is built on the :term[blueprint] are still there underneath, as context.

The colour is the message. **Orange is your decision**: what is listed will stop loading. Spook tells you so, and installs it anyway if you say so. **Red is Spook's**: it will not write this one at all.

There is exactly one red case. A :term[blueprint] that says it needs a newer Home Assistant than you are running cannot work on your installation, whatever you do to your :term[automations]{to="automation"}. Writing it would break everything on it, with no way out but upgrading Home Assistant.

Everything else is orange, including an update that adds a setting nobody has filled in yet. Those :term[automations]{to="automation"} do stop loading, and the dialog says so clearly. But updating first and filling in the new setting afterwards is a normal way to do it, and that choice is yours. Nothing is lost either: a stopped automation keeps its configuration and its ID, its editor opens it as normal, and you fill in what the new version asks for. Ticking **Create backup** first means you can put the :term[blueprint] back as well.

Matter and ZHA put much the same warning in front of a firmware update, for much the same reason.

#### About those version numbers

They look like `a1b2c3d4`. Blueprints have no version. There is nowhere in a blueprint to put one: the format refuses anything it does not recognise, so an author cannot add one even if they wanted to.

So Spook uses a fingerprint of the contents instead. Same fingerprint, same blueprint. A different one means something in it changed. It cannot tell you whether that change is newer or better, only that it is not what you have.

The fingerprint is taken from what a blueprint says, not from how the file is laid out. Home Assistant does not keep the bytes it downloaded. It parses a blueprint and writes it back out in its own formatting, and that formatting can differ between installations and Home Assistant releases: line width, quoting, whether an emoji is written out or escaped. None of that changes what the blueprint does, so none of it changes the fingerprint. Neither does the address it came from, which Home Assistant stores inside the blueprint on the way in, nor the order of the settings it fills in for a selector the author left blank: `multiple`, `reorder` and the like are Home Assistant's doing, not the blueprint's.

Comments and indentation are not part of it either, since neither survives being parsed. Reordering any other key is, though. Home Assistant renders some of them in the order they are written, a `variables:` block among them, so moving two keys around can change what a blueprint does. Spook keeps that order, and does not try to work out which mappings are the executable ones. Guessing wrong there would mean missing a real update, which is worse than mentioning one too many.

#### When an update would break your automations

An input without a default has to be filled in by whoever uses the blueprint. If a new version asks for one your automations do not set, every automation on that blueprint stops loading the moment the file is written, and the version they did work with is gone.

Spook checks before it writes anything, and uses Home Assistant's own rules for what an input needs. If an update would leave your :term[automations]{to="automation"} short, it names them, and the settings each one is missing, above everything else in the dialog. It still installs if you ask it to: those :term[automations]{to="automation"} stop loading, and they keep everything you set and their editors still open, so you fill the new setting in and they come back.

It checks the other way round too. A :term[blueprint] can be valid as a blueprint while what comes out of it is not something Home Assistant will take. The blueprint format says nothing about triggers, actions or a script's sequence. So every :term[automation] and :term[script] on the blueprint is built against the new version and put through the same validation a reload would, and anything that would not load is named the same way. That one is for the blueprint's author to fix, not you: no setting you fill in will change it.

And where it cannot tell, it says so separately. Reading what an :term[automation] supplies to a blueprint relies on something Home Assistant does not offer publicly, and when that is out of reach Spook has nothing to go on. Those are listed as not known, not as broken: an :term[automation] Spook cannot read may be perfectly fine.

A :term[blueprint] that says it needs a newer Home Assistant than the one you are running is the one thing Spook refuses. Writing it would break every :term[automation] on it, and nothing you do to your own :term[automations]{to="automation"} fixes that.

::warning
If you edited an imported blueprint by hand, Spook has no way of telling your changes apart from the author's. It will report an update, because what you have is no longer what is at the address. Installing it will write over your work.

If you have made a blueprint your own, take the `source_url:` line out of the file. There is then nothing to follow, the update entity goes away on its own, and the blueprint is yours. That is also the way to stop following a blueprint you no longer want updates for.

::

::note
Community forum topics sometimes hold more than one blueprint, and every one of them is imported with the address of the topic, not of the blueprint itself. Home Assistant takes the first it finds at that address, so following it can land on a different blueprint entirely.

Blueprints carry no identity of their own, so the most that can be asked is that what comes back is the same kind of blueprint and still goes by the same name. If it does not, Spook leaves it alone and says why in the dialog. It will not offer to write somebody else's blueprint over yours.

The cost of that is an author who renames their blueprint: Spook stops following it, and the dialog will tell you what the address leads to now. Re-import it from the blueprint page and it picks up again.

::

## Actions

Spook adds one action for blueprints. You find it wherever you add an action, marked with a 👻.

### Import blueprint

Downloads an automation or script blueprint from a URL, and imports it.

Handy when importing is part of something bigger: a script that sets up a new installation with the blueprints you always use, or one that pulls in a whole list at once. For a single blueprint, the import button on the blueprints page is the better way: it shows you the blueprint, and any errors or warnings, before importing it.

**How to use it**

1. Open the automation or script that should do the importing, and select **Add action**.
2. Search for **import blueprint**, and select **Blueprint: Import blueprint 👻**.
3. Fill in **URL** with the address of the blueprint, like the link to its topic on the community forum.
4. Select **Save**.

Just want to see it work? [Try this action](https://my.home-assistant.io/redirect/developer_call_service/?service=blueprint.import) opens it in your Home Assistant, ready to run once.

## Use cases

What people use this for:

- Import a blueprint from an automation or script, for example to set up the same blueprints on a fresh Home Assistant without importing each one by hand.
- Get told when the author of a blueprint you use has changed it. Beats finding out months later that the bug you worked around was fixed all along.
- Put the blueprint update entities in an automation of your own, so a notification goes out when one of them has something new to say.
