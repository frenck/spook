A :term[dashboard] in :term[Home Assistant] is the screen you use to see and control your home: cards with your lights, sensors and cameras. Dashboards are extremely flexible, and there is quite a community around creating the fanciest dashboards you've ever seen. But with great power comes great responsibility. Cards keep pointing at things long after those were renamed or removed, and a dashboard has a lot of cards.

Spook looks through your dashboards for you, and tells you when a card points at something that is not there anymore.

::note
You might see the term "Lovelace" everywhere in the community. This is the internal codename of the current dashboard system used in Home Assistant, which was used until it fully replaced the old (and now removed) state UI from before. The term "Lovelace" is still used by many in the community and is, of course, still present in the codebase of Home Assistant.

TL;DR: "Lovelace" is the dashboard system of Home Assistant and is nowadays just referred to as "Dashboards".

::

## Repairs

Spook looks through your dashboards for things that can no longer work, and tells you in the :term[repairs dashboard]{to="repairs"}. Each repair names the dashboard and what is wrong with it.

Fixing one usually goes the same way: select the name of the dashboard in the repair to open it, select the pencil to edit, change what the repair points at, and select **Save**. Spook looks again when you save, and takes the repair away by itself. New to this? Follow [Fix your first repair](/fix-your-first-repair).

### Unknown referenced entities

A card on a dashboard uses an entity that no longer exists, usually because it was renamed, replaced or removed. The card shows an error, or a row that says the entity is not available.

::screenshot{name="repair-dashboard-unknown-entities" alt="A repair raised by Spook for a dashboard."}
Spook found an issue with an dashboard that is using non-existing entities.

::

**How to fix it:** Select the name of the dashboard in the repair to open it, and select the pencil to edit it. Find the card the repair points at, pick the right entity or remove it, and select **Save**. The guide [Fix your first repair](/fix-your-first-repair) walks you through the same steps for an automation. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every :term[entity]{to="entity"} the cards on your dashboards use. When an :term[entity ID] does not exist, it raises a repair that names the dashboard and the missing entity ID.

:::

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Spook does not know every option of every card. Third-party cards in particular can be configured differently, and Spook can miss an unknown entity ID there.
- Most third-party cards use the same keys as Home Assistant's own (`entity`, `entities`), and those are read on any card. Bubble Card has a few of its own, which Spook knows about: the entity that opens a pop-up (`trigger_entity`), and the numbered buttons of a horizontal buttons stack (`1_entity`, `1_pir_sensor`, and so on).
- Entities named inside templates, or in a card's own variables, are not checked. What a template ends up pointing at cannot be known without running it.

:::
::

### Unknown referenced areas

A dashboard uses an area that no longer exists, usually because the area was renamed, merged or removed. Whatever uses it no longer shows what you meant.

**How to fix it:** Open the dashboard the repair names, and select the pencil to edit it. Pick an area that exists where the missing one is used, or remove it, and select **Save**. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at every :term[area]{to="area"} your dashboards use. An area can be referenced in more than one way: by an area card, by the area view strategy, by the area views of a Home dashboard you took control of, by the areas dashboard strategy listing areas to hide or order, by the Mushroom template card, and by an `area_id` used as the target of an action. The word `area` on other cards is left alone, since some use it for a caption. Spook looks for all of them and raises a repair naming the dashboard and the areas that are missing.

What you see depends on where the reference sits. The frontend decides that, so this page does not promise you a particular symptom. Spook tells you which dashboard names which missing area.

:::
::

### Unknown referenced attributes

A card shows, or a condition checks, an attribute its entity does not have, like `brightness` on a plain switch. An attribute is an extra detail an entity carries next to its state. The card stays empty or the condition never passes, and you get no error.

**How to fix it:** Select the name of the dashboard in the repair to open it, and select the pencil to edit it. In the card the repair points at, pick an attribute the entity has, and select **Save**. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the attributes your dashboards show and check: the `attribute` of the entity card, the gauge card, the attribute row, the state label element and the entities of a picture glance card, the attribute a map card labels its markers with, the attributes in the `state_content` of a tile card or an entity badge, and the `attribute` of state and numeric state conditions and of entity filter state filters. When a dashboard uses an attribute its entity does not have, Spook raises a repair. It names the dashboard, the attribute and the entity, and what was most likely meant when Spook is near certain of it.

A card showing an attribute that never shows up stays empty, and a condition checking one never passes. You get no error.

Spook holds these to the same evidence as the attributes used in [automations](/automation#unknown-referenced-attributes): an attribute is only reported when Spook cannot find it anywhere. Not on the entity right now, not as something that kind of entity offers in Home Assistant, and not in anything the recorder remembers the entity having. An entity the recorder does not record is only checked for attributes that differ from a real one in upper and lower case alone, like `Brightness`.

:::
::

### Unknown referenced states

A card is set to show or hide on a state its entity is never in, like `On` for a light that is `on` or `off`. That condition never passes, so the card never shows (or never hides).

**How to fix it:** Select the name of the dashboard in the repair to open it, and select the pencil to edit it. In the condition the repair points at, use a state the entity can be in, and select **Save**. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the states your dashboards check for: the `state` and `state_not` of visibility conditions on cards, badges and sections, of the conditions of a conditional card, row or picture element, and of the filters of an entity filter card or badge. The states a picture card or image element picks an image or a filter for count too. When a dashboard checks for a state its entity is never in, like `On` for a light that is `on` or `off`, Spook raises a repair. It names the dashboard, the state and the entity, and what was most likely meant when Spook is near certain of it.

Only entities whose states are a fixed set are checked, and on the same evidence as the states used in [automations](/automation#unknown-referenced-states). A plain sensor can be anything, so it is never checked.

The frontend compares a state that looks like an entity ID with the state of that entity as well, so those are never reported. Neither is a condition without an entity of its own, unless it sits on a card or badge whose entity it takes. A filter on an entity filter card is held against every entity on it, and is only reported when none of them can ever pass it.

Spook looks ten minutes after Home Assistant starts, when the recorder has settled. After that it looks again when a dashboard is saved, when an entity is added or removed, when the entity registry changes, when an integration loads, and once a day. The same goes for unknown attributes.

:::

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Third-party cards are not checked at all, and neither is anything inside them. They can use the same keys as Home Assistant's own cards and mean something else entirely.
- Templates are not checked, and neither are attributes, states or entities that are only worked out while running.
- A state written as a number, or as `true` or `false`, is not checked. How the frontend compares those depends on where the condition is evaluated.

:::
::

### Unknown actions

A button or card on a dashboard performs an action that does not exist, usually because a script was renamed or removed, or the integration behind it is gone. Tapping it does nothing, and says nothing either.

**How to fix it:** Select the name of the dashboard in the repair to open it, and select the pencil to edit it. In the tap, hold or double tap action of the card the repair points at, pick an action that exists or remove it, and select **Save**. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the :term[actions]{to="performing actions"} the buttons and cards on your dashboards perform. A tap, hold or double tap action set to perform an action that does not exist does nothing when used, and shows no error either. Spook raises a repair naming the dashboard and the actions that are missing.

This usually happens when a script was renamed or removed, or when the integration providing the action was removed. Spook looks again when an integration loads and when actions come and go, so an integration that takes a while to start does not leave a repair behind.

Actions of an integration you disabled are not reported: switched off on purpose is not gone. Once you enable the integration again, they are checked as usual.

:::

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Spook reads every action set to perform an action, under whatever name a card gives it, so third-party cards using the same shape as Home Assistant's own are covered too.
- An action that is a template, like the JavaScript templates of button-card, is not checked. What it ends up performing cannot be known without running it.

:::
::

### Unknown views

A button or card navigates to a view that does not exist. Tapping it opens the first view of that dashboard instead, which looks like the button is broken.

**How to fix it:** Select the name of the dashboard in the repair to open it, and select the pencil to edit it. Point the navigation of the card the repair names at a view that exists, and select **Save**. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at where your dashboards navigate to: a tap, hold or double tap action set to navigate, the navigation path of an area card, and the back button of a subview. When that is a view of a dashboard that does not have it, Spook raises a repair naming the dashboard that navigates there and the paths that lead nowhere.

The frontend does not tell you when a view is missing. It opens the first view of that dashboard instead, with the address still showing the view you asked for. This usually happens when a view was renamed, moved to another dashboard, or removed.

A view is found by its path, or by its number counting from 0, the same way the frontend finds it. So `/lovelace/kitchen` needs a view with the path `kitchen`, and `/lovelace/2` needs a third view, or one with the path `2`.

:::

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Only a path to a view of a dashboard you made in the UI is checked. A YAML dashboard can pull its views in from other files, and the views of a dashboard run by a strategy, like the areas dashboard, are only made when it opens. Spook cannot see all of those views, so it does not judge them.
- Paths to anything that is not a dashboard, like `/config`, `/history` or an add-on, are not checked.
- A relative path, or a `#` on its own like the pop-ups of Bubble Card, depends on where you are when you tap it, and is not checked. A `#` after a view is fine: the view it is on is checked.
- A path that is a template, or uses a card's own variables, is not checked. Where it ends up cannot be known without running it.

:::
::

### Unknown icons

A dashboard uses an icon that Home Assistant does not have, usually because of a typo or a renamed icon. The card, badge or view shows an empty spot where the icon should be.

**How to fix it:** Select the name of the dashboard in the repair to open it, and select the pencil to edit it. Pick an icon that exists in the card the repair points at, and select **Save**. The icon of the dashboard in the sidebar is changed in **Settings** > **Dashboards**. When Spook is nearly certain what you meant, the repair says so. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the icons your dashboards show: on cards, rows, badges, picture elements and views, and the icon of the dashboard in the sidebar. An `mdi:` icon that is not in the Material Design Icons that come with Home Assistant is drawn as an empty spot. No error, nothing in the logs. Spook raises a repair naming the dashboard and the icons that do not exist, and suggests the icon you most likely meant when it is nearly certain.

This usually happens with a typo, an icon that was renamed or removed, or one picked from the Material Design Icons website that is newer than the version Home Assistant comes with. The repair says which version that is.

:::

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Only icons starting with `mdi:` are checked. The older `hass:` prefix, and icons from sets you added, like those from HACS, are left alone.
- Icons inside a third-party card are left alone: what that card does with them is up to the card. A card of Home Assistant's own inside one, like in a custom stack, is checked.
- An icon that is a template is not checked. What it ends up as cannot be known without running it. That includes the JavaScript templates of button-card.
- An icon in the data a button hands to an action is not checked here.
- The list of icons is read from the frontend Home Assistant has installed. A frontend run from a development build is not taken into account, and a frontend without that list means nothing is checked.

:::
::

### Removed users

A card, badge, section or view is only shown to certain users, and one of those users was removed. If it was only shown to removed users, nobody sees it anymore.

**How to fix it:** Select the name of the dashboard in the repair to open it, and select the pencil to edit it. In the visibility of the card the repair points at, pick the users who should see it, or remove the condition, and select **Save**. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the users your dashboards name: the users of a user condition in the visibility of a card, badge or section (also nested in `and`, `or` or `not`), in the conditions of a conditional card, row or element, the users a view is visible to, and the users exempted from the confirmation of an action. When one of those users no longer exists, Spook raises a repair naming the dashboard and the user IDs it cannot find.

Home Assistant gives every user a random ID and never hands the same one out twice, so an ID no user has belongs to a user that was removed. The frontend does not tell you. A card, badge, section or view that was only shown to removed users is now shown to nobody, and an exemption for a removed user does nothing.

:::

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Only something shaped like a user ID is checked. A user written down by name never matched anybody, and is not a user that was removed.
- Custom cards are not checked inside, as their keys can mean anything. The visibility you give a custom card is checked, as the frontend handles that for every card.
- A dashboard run by a strategy, like the areas dashboard, is not checked.

:::
::

### Unknown themes

A card, section or view asks for a theme that does not exist, usually because the theme was renamed or its file removed. It gets the default look instead, without an error.

**How to fix it:** Select the name of the dashboard in the repair to open it, and select the pencil to edit it. Pick a theme that exists where the missing one is used, and select **Save**. Or add the theme back. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks at the themes your dashboards use: the theme of a view, of a section, and of the cards that take one, also inside stacks, grids, conditional cards and the header and footer of a sections view. When that theme does not exist, Spook raises a repair naming the dashboard and the themes that are missing.

The frontend does not tell you when a theme is missing. It only puts on a theme it has, so a card or view asking for one that is gone gets the default look. This usually happens when a theme was renamed, or the file it came from was removed.

A theme is found by its name, exactly as written, so `midnight` is not `Midnight`. `default` and `none` are fine: those are built in, not themes of your own. So is `Backend-selected`, which older versions of the theme picker wrote when no theme was picked. Spook looks again when the themes are reloaded, so adding a theme back clears the repair as well.

:::

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- Only the cards that put on a theme are checked. A theme on any other card, like a tile card or a stack, does nothing either way.
- Only what the view's layout draws is checked. A panel view shows its first card only, and the sections, header and footer of a view that is not a sections view are never shown.
- Custom cards, and the cards inside them, are not checked. What a custom card does with a `theme` is up to the card. The theme of a custom view or section is checked, as the frontend puts that one on itself.
- A theme that is a template, or uses a card's own variables, is not checked.
- Views, sections and dashboards run by a strategy are not checked. Those are only made when they open.

:::
::

### Missing dashboard resources

A dashboard resource points at a file that is not there, usually because a custom card was removed but its resource stayed behind. Every browser tries to load that file, on every page load, and it never arrives.

**How to fix it:** Go to **Settings** > **Dashboards**, open the menu in the top right, and select **Resources** (the repair links there too). Remove or correct the resources the repair lists. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Dashboard resources tell Home Assistant which extra JavaScript and CSS files to load. That is how custom cards get there. Spook checks the ones it can: a resource served from `/local/` or `/hacsfiles/` maps to a file on disk, so Spook can see whether that file is there. When it is not, Spook raises a repair that lists those resources.

Resources on an external URL, or served by an integration, are skipped on purpose. Spook cannot check those without fetching them.

A missing local resource usually means a custom card was removed but its resource stayed behind. Every browser then asks for that file on every page load.

:::
::

### Duplicate dashboard resources

The same dashboard resource is listed more than once, usually after updating a custom card. The browser loads both copies, the card trips over itself, and you see a broken card.

::screenshot{name="repair-duplicate-resources" alt="The repair for a dashboard resource listed twice, with the choice to clear the extra copies."}
The same card, loaded twice, and the offer to keep one.

::

**How to fix it:** Select the repair. Spook offers three ways out:

- **Clear the extra copies, keep the most recent**: Spook removes every copy but the last one added. For a card updated by adding a resource instead of editing one, that is the version you meant to end up with.
- **Let me fix it myself**: Points you at **Settings** > **Dashboards** > **Resources**, and leaves the repair in place until you have.
- **Leave them, stop telling me**: Keeps the resources as they are and stops Spook mentioning that one again.

Resources listed in YAML cannot be changed by Spook. For those, the repair tells you which file to edit. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

The same resource can be listed more than once. Every resource you add gets a fresh ID, and what it points at is not compared with the others.

The usual way in is updating a custom card. The new version wants a new cache-busting URL, so `/local/some-card.js?v=1` gains a neighbour at `?v=2` instead of being edited. Both stay. The browser treats two URLs as two files and loads both, the card tries to register itself twice, and the second attempt throws. What you see is a broken card, so you look at the card, not at the resource list.

Spook raises a repair naming each resource that appears more than once, and the URLs involved where they differ.

For a resource served from `/local/` or `/hacsfiles/` the path is a file on disk, so two URLs differing only in their query string are the same file and are reported as duplicates.

For any other resource, only an exact repeat counts. A query string on somebody else's server can be the difference between two different files, and Spook does not guess.

The resource type is part of the comparison either way. Home Assistant loads a `module` differently from a `css`, so the same URL listed under two types is two instructions, not one repeated. Spook leaves those alone.

Resources listed in YAML are static, so there is nothing Spook can delete for you there. Those duplicates are still reported, and choosing to fix one tells you which file to edit.

:::
::

### Public files in the www folder

Home Assistant serves everything in the `www` folder of your configuration at `/local/`, without a login. That is on purpose: browsers load custom cards and dashboard images from it with a plain link, and a plain link cannot carry a login. It also means anybody who can reach your Home Assistant can download what is in there, if they know or can guess the name of the file.

Custom cards and your own images are not the only things that end up there. Some :term[integrations]{to="integration"} store files in `www` to show them on a :term[dashboard], like camera snapshots or previews of 3D prints. It is easy to miss that those are public too.

Spook raises a repair for every folder in `www` holding files that nobody seems to have put there on purpose.

**How to fix it:** find out which integration writes to the folder, and whether it can store its files somewhere else. Are the files fine to be public? Ignore the repair: Spook then keeps quiet about that folder, also when new files show up in it. The repair disappears by itself once it is fixed.

::accordion
:::accordion-item{label="How Spook checks this" icon="i-mdi-magnify"}

Spook looks through the `www` folder when it starts, when a dashboard or theme changes, and every hour. It leaves alone:

- The `community` folder, where the Marketplace installs dashboard cards (:term[HACS] did so before Home Assistant 2026.11).
- Any folder holding frontend code (JavaScript or CSS). That is a card or a theme, images and all.
- Hidden files and folders.
- Files a dashboard or theme links to with `/local/`, written out or URL-encoded.

:::

:::accordion-item{label="Known limitations" icon="i-mdi-alert-outline"}

- While a dashboard cannot be read, for example because of an error in its YAML, Spook does not know which files it shows. It then skips the check, keeps the repairs it raised before, and logs a warning.
- Only dashboards and themes are checked for files in use. A file sent along with a notification, or linked to from a template, is reported as unused.
- A folder holding frontend code is skipped as a whole, even when an integration writes other files into it as well.

:::
::
